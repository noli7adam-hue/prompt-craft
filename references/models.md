# Модельная шпаргалка: специфика платформ (2025–2026)

Читай этот файл, когда целевая модель — не Claude, или когда нужна точная специфика платформы. Названия конкретных версий волатильны — сверяй с актуальной документацией вендора (статус проверки по каждому факту — в `sources.md`), но категории (reasoning vs обычные) и принципы устойчивы.

## Reasoning vs обычные модели — сводная таблица

| Аспект | Обычные (GPT-класс, Haiku/Flash/mini) | Reasoning (GPT-5.x, Claude thinking, Gemini 3 thinking) |
|---|---|---|
| Метафора (OpenAI) | «младший коллега» — точные инструкции | «старший коллега» — цель + критерий готовности |
| CoT «думай пошагово» | помогает на многошаговых задачах | избыточен/вреден (+2.9…3.1% при +20–80% задержки; Gemini Flash −3.3%) |
| Few-shot | 2–5 примеров полезны | часто ухудшает; начинай с zero-shot |
| Контекст в RAG | можно щедро | только отфильтрованное релевантное |
| Управление глубиной | через промпт | через ручку API |
| Самопроверка | просить явно | частично встроена; задавай критерий готовности |

Где CoT всё ещё нужен: нереясонинг-модели на математике/логике/отладке; некоторые open-source семейства (Gemma3, Qwen-Math) до сих пор оцениваются few-shot CoT.

---

## Claude (Anthropic)

**Сильные стороны:** XML-структурирование, буквальное следование инструкциям, длинные документы, агентный код.

- **XML — родной формат.** `<instructions>`, `<context>`, `<examples>`, мульти-документ `<document>` → `<source>` + `<document_content>`. Модель дообучена уважать произвольные иерархические теги.
- **Буквальность.** Поведение «выше и сверх» запрашивай явно; Claude воспроизведёт любые случайные паттерны из примеров. Контекст-мотивация («почему») улучшает обобщение.
- **Длинный контекст:** данные (20k+ токенов) вверху, запрос в конце — до +30% качества. Для длинных документов: сначала процитировать релевантные части, затем отвечать.
- **Ризонинг:** adaptive thinking + параметр `effort` (low → max); `budget_tokens` deprecated. Extended thinking — только когда заметно улучшит качество: «В сомнении — отвечай напрямую». Против overthinking: «Выбери подход и придерживайся его. Не пересматривай решения без новой противоречащей информации».
- **При выключенном thinking** модель чувствительна к слову «think» — используй «consider», «evaluate», «reason through».
- **Prefill не поддерживается на 4.6+** (ошибка 400) — формат задавай явной инструкцией или через tool use.
- **Temperature/top_p на новейших моделях менять нельзя.**
- **Дозирование действий** — две официальные заготовки: `<default_to_action>` (действуй по умолчанию, для агентов) vs `<do_not_act_before_instructions>` (не меняй без явной просьбы).
- **Параллельные tool-call:** официальный блок:
```
<use_parallel_tool_calls>
Если ты собираешься вызвать несколько инструментов и между вызовами нет зависимостей,
делай все независимые вызовы параллельно. Если вызов зависит от результата предыдущего —
вызывай последовательно. Никогда не используй заглушки и не угадывай параметры.
</use_parallel_tool_calls>
```
Обратная проблема: новые Sonnet агрессивно параллелят — иногда нужно явно просить последовательность.
- **Анти-оверинжиниринг (агентный код):**
```
Избегай оверинжиниринга. Делай только то, что прямо запрошено или явно необходимо.
- Не добавляй фичи, рефакторинг и «улучшения» сверх запроса.
- Не добавляй докстринги/комментарии к коду, который не менял.
- Не добавляй обработку ошибок для сценариев, которые не могут случиться.
```
- **Проза вместо булитов:** спецблок `<avoid_excessive_markdown_and_bullet_points>`; и принцип «согласуй стиль промпта со стилем ответа» — уберёшь markdown из промпта → меньше markdown в ответе.
- **Смягчение настойчивости:** «CRITICAL: YOU MUST» из эпохи 3.x вызывает overtriggering — заменяй на «Use this tool when…».

## GPT-5.x / OpenAI

**Сильные стороны:** агентные пайплайны, Structured Outputs, управляемость параметрами.

- **Два класса моделей:** GPT («рабочие лошадки») — точные инструкции; reasoning — цель + ограничения + критерий готовности. Официально для новейших: «State the expected outcome and success criteria. Reduce or remove detailed step-by-step process guidance. Remove output schema definitions from the prompt — use Structured Outputs instead». При миграции старых промптов — «начинать с чистого листа».
- **Ручки:** `reasoning.effort` + `verbosity` (low/medium/high). Набор уровней зависит от модели: у GPT-5.6 — `none`/`low`/`medium`/`high`/`xhigh`/`max`, дефолт `medium`; `minimal` остался только на GPT-5, на 5.1+ он отклоняется. `none` — режим без reasoning-токенов для латентности. Правило: **одно изменение за раз** — сначала модель, потом effort, потом промпт, эвалы после каждого шага.
- **Агентность:** блоки `<persistence>` (продолжай, пока запрос не решён; документируй допущения, не переспрашивай), `<tool_preambles>` (переформулируй цель → план → комментарии по ходу → сводка), лимит tool-call («не более N вызовов»). Responses API сохраняет reasoning между вызовами инструментов.
```
<persistence>
Ты агент — продолжай, пока запрос не решён полностью. Не останавливайся на неопределённости.
Не проси подтверждать допущения — документируй их, действуй и корректируйся.
</persistence>
```
- **Контракт вывода:**
```
<output_contract>
- Верни ровно запрошенные секции в запрошенном порядке.
- Если задан формат (JSON, Markdown, SQL, XML) — выводи только его.
</output_contract>
```
- **RAG для reasoning-моделей:** только отфильтрованный релевантный контекст, не «всё подряд».
- System-сообщение у reasoning-серии конвертируется в developer-сообщение — практически работает как прежний system prompt.

## Gemini 3 (Google)

**Сильные стороны:** длинный контекст, мультимодальность, grounding через Google Search / Vertex.

- **Порядок обратный Claude:** при длинном контексте данные СВЕРХУ, инструкции и вопрос — В САМОМ КОНЦЕ, с якорем «Based on the entire document above…» и явным «используй ТОЛЬКО предоставленный документ как источник истины».
- **Sampling-параметры:** на Gemini 3 — `temperature=1.0`, не менять (риск зацикливания). На поколении 3.5+ `temperature`/`top_p`/`top_k` больше не рекомендованы и игнорируются бэкендом — удаляй их из конфига, а не выставляй в 1.0; `frequency_penalty`, `presence_penalty`, `candidate_count` вызывают ошибку.
- **Краткость обязательна:** «please» и вежливая вода воспринимаются как шум. Gemini 3 по умолчанию лаконичен — «разговорчивость» запрашивай явно.
- **Не смешивать XML и markdown** — выбери один формат.
- **Широкие негативные ограничения запрещены:** «do not infer/guess» ломает базовую логику и арифметику — заменяй позитивным «используй предоставленный контекст для вычислений». При сложных запросах модель «роняет» негативные ограничения — критичные правила ставь в конец (рядом с вопросом).
- **Персона перевешивает инструкции:** Gemini воспринимает назначенную персону настолько серьёзно, что может игнорировать правила ради неё — не создавай противоречий.
- **Ризонинг:** `thinking_level` (minimal/low/medium/high; набор зависит от модели — `minimal` есть не везде). Заменил `thinking_budget`; вместе они не передаются. В поколении 3.5+ дефолт сменился с high на medium — задавай уровень явно. Для скорости — LOW + «think silently».
- **Мультимодальность:** явно маркируй входы («Image 1», «Video 2») и ссылайся на модальность в инструкции.
- **Few-shot:** строго единый формат всех примеров, иначе ответ «съезжает»; не перегружать примерами (оверфит формату).
- **Grounding:** для grounding-режима temperature 1.0; анти-галлюцинация через двухшаговую верификацию: «Сначала проверь, есть ли у тебя доступ к X. Если нет — ответь "No Info" и ОСТАНОВИСЬ».

## Perplexity (Sonar)

**Главное: это поисковик, а не чат.** Официально: «only the user message is used to drive that search. The system prompt is not visible to search». Значит — «query engineering» важнее prompt engineering.

- **Разделение ролей:** `instructions` (системный промпт) задаёт роль, тон, форматирование и правила граундинга; `input` (пользовательское сообщение) сеет поисковый запрос — конкретность здесь напрямую улучшает извлечение. Вылощенный системный промпт не спасёт расплывчатый запрос.
- **Фильтры — параметрами, не прозой:** «ищи только в Wikipedia» в промпте не работает. Используй `search_domain_filter` (до 20 доменов, `-` для исключения), `search_recency_filter` (hour/day/week/month), `search_context_size` (low/medium/high).
- **Не просить URL в прозе** — модель цитирует по индексу; авторитетный список источников — поля `citations`/`search_results`.
- **Не few-shot-ить контентом** — поиск «зацепится» за тему примера. Few-shot структуры допустим; для гарантированной формы — `response_format`.
- **Разрешение сказать «не найдено»:** обязательный блок против галлюцинаций:
```
Отвечай только на основе результатов поиска. Если результаты не содержат ответа —
скажи об этом явно, а не угадывай. Если результаты смежные, но не совпадают
(другой год, материнская компания, похожий продукт) — заяви о несоответствии до ответа.
```
- **Хороший запрос** = конкретика + временной горизонт + тип источника: «Какие рекомендации FDA выпустила по ИИ в медицинских устройствах за последний год и какие категории устройств они покрывают?» лучше, чем «Расскажи про правила FDA по ИИ». «Найди рецензируемые исследования» лучше, чем «найди исследования».
- **Модели:** sonar (быстро), sonar-pro (синтез), sonar-reasoning-pro (CoT+поиск), sonar-deep-research (автономный, сотни источников).
- Установка `instructions` с пресетом ЗАМЕНЯЕТ системный промпт пресета, а не дополняет.
- **Agent API:** Chat Completions у Sonar живёт на объявленный срок поддержки, дальше — Agent API. Если промпт пишется под продакшн, скажи пользователю про горизонт миграции и сверь дату по `sources.md`; сам промпт при этом переносится почти без изменений — меняется обвязка вызова, а не текст.

## Grok (xAI)

- Глубина — параметром `reasoning={"effort": …}`, не текстом; набор уровней сверяй по документации xAI.
- В остальном рассматривай как reasoning-модель общего вида: outcome-first, zero-shot на старте, критерий готовности вместо пошагового рецепта.
- Для моделей с встроенным поиском действует то же правило, что у Perplexity: конкретность пользовательского запроса важнее вылизанного системного промпта.

## Mistral

- Глубина — `reasoning_effort` в chat completions; нативные `magistral-*` устарели.
- В мультитёрне возвращай в историю **полное** assistant-сообщение вместе с `ThinkChunk`, иначе модель теряет свой ризонинг между ходами.
- Structured output — через встроенный механизм схемы, а не описанием в прозе.

## Open-weight (Qwen, DeepSeek, Kimi, GLM, Llama)

- **Сначала определи, включён ли reasoning** — одно и то же семейство выпускается в обоих режимах, и от этого зависит весь дизайн промпта. Есть режим thinking → работай как с reasoning-моделью; нет → классика с CoT и few-shot.
- **Формат чат-шаблона важнее формулировок:** соблюдай тот шаблон ролей и спецтокены, которые заявлены для конкретного чекпоинта; расхождение ломает следование инструкциям сильнее любых правок текста.
- **Sampling-параметры — часть промпта.** Для локальных моделей рекомендованные значения `temperature`/`top_p` публикуются вместе с весами и заметно влияют на стабильность; выноси их в блок «Параметры API» и бери из карточки модели, а не по памяти.
- Инструкции держи короче и однозначнее, чем для фронтир-моделей: длинные многослойные контракты они выполняют выборочно. Критичное — ближе к концу.
- Некоторые семейства (Gemma3, Qwen-Math) до сих пор оцениваются few-shot CoT — примеры здесь остаются рабочим рычагом.

## Выбор платформы под задачу

- Источники, свежие данные, цитаты → Perplexity (или Gemini grounding)
- Длинные документы, мультимодальность → Gemini
- Структурный контроль, агентный код, надёжное следование инструкциям → Claude
- Агентные пайплайны, Structured Outputs → OpenAI GPT-5.x
