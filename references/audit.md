# Аудит и улучшение существующего промпта

Когда пользователь приносит свой промпт и просит «улучшить» или жалуется, что модель работает не так — следуй этому процессу.

## Шаг 1: Спроси о симптомах (если неясно)

Не переписывай вслепую. Если пользователь не сказал, что именно идёт не так, спроси одно из:

- Что модель делает сейчас и что должна делать вместо этого?
- Есть ли пример входа, на котором она ломается?
- Какая целевая модель и включён ли reasoning/thinking? (это меняет диагноз кардинально)

Если симптомы понятны из контекста — пропускай этот шаг.

## Шаг 2: Прогони промпт через диагностический чек-лист

Иди по списку и помечай, что нашёл. Это твой план правок.

### Несоответствие классу модели (проверяй ПЕРВЫМ)

- [ ] **Пошаговый CoT / «думай пошагово» на reasoning-модели** — душит внутренний ризонинг; заменить на outcome-first (цель + ограничения + критерий готовности)
- [ ] **Пачка few-shot примеров на reasoning-модели** — часто деградация; попробовать zero-shot
- [ ] **Глубина ризонинга «магическими словами»** (ultrathink и пр.) — deprecated; управлять параметром API
- [ ] **Наоборот: обычная модель без ризонинга оставлена без CoT/примеров** на многошаговой задаче

### Структурные проблемы

- [ ] **Нет роли** или роль размыта («ты помощник»); или роль конфликтует с задачей (опасно на Gemini)
- [ ] **Контекст после задачи** (для Claude/GPT), или наоборот — **инструкции не в конце** (для Gemini с длинным контекстом)
- [ ] **Нет структуры** — всё одной стеной текста
- [ ] **Смешаны XML и markdown** в одном промпте (критично для Gemini)
- [ ] **Длинный документ зашит в середину** — «lost in the middle»
- [ ] **Плейсхолдер не в конце** или не обёрнут в семантический тег
- [ ] **Продакшн-промпт: волатильное (timestamp, состояние) в начале** — ломает кэш

### Проблемы инструкций

- [ ] **Только запреты** без альтернатив («не делай Х»)
- [ ] **Широкие негативные ограничения на Gemini** («do not infer/guess») — ломают логику
- [ ] **Капс и угрозы** («КРИТИЧНО! ТЫ ОБЯЗАН!») — overtriggering на новых Claude
- [ ] **Противоречивые правила** (краток + исчерпывающ; формальный + дружеский)
- [ ] **Пустые хвалилки** («будь умным, креативным, точным»)
- [ ] **Слишком много ролей сразу** («ты эксперт во всём»)
- [ ] **Намёки вместо прямых указаний** — новые модели буквальны и недодают
- [ ] **Вежливая вода на Gemini** («please», лишние обороты) — шум

### Проблемы примеров

- [ ] **Примеров нет**, хотя задача нетривиальна и модель обычная
- [ ] **Один-единственный пример** — модель решит, что все случаи такие
- [ ] **Все примеры однотипны** — нет разнообразия; сильнейший не последним
- [ ] **Разный формат примеров** (особенно критично для Gemini)
- [ ] **Случайные паттерны в примерах** (все начинаются с одного слова, всё одной длины)
- [ ] **Примеры противоречат правилам** — модель доверится примерам
- [ ] **Чувствительные данные в примерах** — могут быть воспроизведены

### Проблемы формата вывода

- [ ] **Формат не описан** — только намёк
- [ ] **JSON-схема в прозе при доступном API-механизме** — перенести в Structured Outputs / tool use / response_schema
- [ ] **JSON без схемы и без примера** — модель сгенерирует правдоподобную, но неверную структуру
- [ ] **Нет указания «без преамбулы»** — модель добавит «Конечно, вот ответ:»
- [ ] **Не сказано про markdown-обёртку** — модель завернёт JSON в ```json блок
- [ ] **Нет валидации + ретрая** на приложенческом уровне (для прода)

### Проблемы краевых случаев

- [ ] **Не сказано, что делать при пустом/некорректном вводе**
- [ ] **Нет тай-брейкера** для пограничных случаев
- [ ] **Нет «escape hatch»** — категории `other`, ответа «не знаю», разрешения сказать «не найдено» (для RAG/поиска — обязательно)

### Безопасность

- [ ] **Промпт ест недоверенный контент** (веб, письма, документы, tool-выводы), а контент не маркирован и не объявлен «данными, не инструкциями»
- [ ] **Секреты/ключи/приватная логика в системном промпте** — считаются скомпрометированными; выносить из промпта
- [ ] **Агент без категоризации действий** — нет human-in-the-loop на необратимом
- [ ] Детали — `security.md`

### Специфика платформ

- [ ] **Prefill на Claude 4.6+** — не поддерживается (400); заменить явной инструкцией формата или tool use
- [ ] **Слово «think» при выключенном thinking на Claude** — заменить на «consider»/«evaluate»
- [ ] **Search-инструкции в системном промпте Perplexity** («ищи только в X») — не работают; фильтры параметрами
- [ ] **Просьба URL в прозе у Perplexity** — брать из `citations`/`search_results`
- [ ] **temperature изменена на Gemini 3** — вернуть 1.0
- [ ] **Мультимодальные входы без маркировки** на Gemini («Image 1», «Video 2»)

### RAG-специфика

- [ ] **«Галлюцинации» лечат промптом, не проверив retrieval** — сначала context recall; если retrieval сломан, промпт не поможет (см. `context-engineering.md`)
- [ ] **Нет паттерна «процитируй, потом отвечай»**
- [ ] **Gold-документ закопан в середину пачки**

## Шаг 3: Сделай дифф, а не переписывай с нуля (если возможно)

Если промпт пользователя в целом разумен — покажи **что именно** меняешь и **почему**, не выбрасывай его работу. Это уважительнее и обучает пользователя.

Формат:

> **Что меняю:**
> 1. Убрал «думай пошагово» — у тебя reasoning-модель, ей это мешает (Wharton 2025: +3% точности за +20–80% задержки); вместо этого добавил критерий готовности.
> 2. Перенёс блок с документами в начало (для Claude контекст предшествует вопросу — до +30% качества).
> 3. Заменил «НЕ ИСПОЛЬЗУЙ MARKDOWN!!!» на `Пиши прозой ровными абзацами` — позитивная формулировка без капса работает надёжнее.
> 4. Добавил два примера для краевых случаев — был только «счастливый путь».
> 5. Вынес JSON-схему из текста в Structured Outputs — гарантия схемы вместо надежды.

Затем — итоговый промпт целиком в кодовом блоке. Если менял несколько вещей — предупреди, что для диагностики лучше вносить правки по одной и замерять (см. `evals.md`).

Если промпт пользователя совсем сырой или в нём фундаментально неверный подход — переписывай с нуля, но **скажи об этом** и объясни почему.

## Шаг 4: Сверь с целью

Прежде чем отдавать результат — мысленно прогони промпт на 1–2 реальных входах, которые пользователь упомянул, плюс на одном краевом. Если модель явно споткнётся — допиливай. Предложи пользователю мини-набор тестовых входов.

## Типовые «быстрые победы»

Если нужно улучшить промпт за минимум правок, эти изменения чаще всего дают наибольший эффект:

1. **Проверить соответствие классу модели** (убрать CoT/примеры с reasoning; добавить их на обычной) — самый крупный рычаг 2025–2026
2. **Добавить 3 разнообразных примера** (обычные модели)
3. **Перенести длинный контекст к краям** по правилам платформы
4. **Описать формат вывода со схемой** или вынести в API-механизм
5. **Заменить «не делай X» на «делай Y»**
6. **Добавить escape hatch** («не знаю» / other / «не найдено»)
7. **Убрать капс и градус накала**
8. **Добавить self-check** в конце (обычные модели) или критерий готовности (reasoning)
