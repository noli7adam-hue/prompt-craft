# Frontier-агентные модели: Claude Opus 5 / Sonnet 5 / Fable 5 и новее

Читай этот файл, когда целевая модель — Claude Opus 5 или новее, когда идёт миграция на новое поколение или когда жалоба звучит так: многословно, лезет за рамки задачи, жжёт токены на перепроверках, плодит субагентов, отчитывается о командах, которых не запускал.

Главный принцип поколения: **промпт настраивается вычитанием.** Thinking включён по умолчанию, модель сама верифицирует работу и сама чинит свои ошибки. Обвязка, написанная под 3.x/4.x, теперь складывается со встроенным поведением и работает против качества.

## Шаг 1: что удалить

Пройди по промпту и вычеркни:

- Инструкции верификации: «дважды проверь», «финальный этап проверки», «перечитай ответ перед отправкой», «пусть субагент-ревьюер проверит твою работу».
- Универсальный CoT: «думай пошагово», «рассуждай в `<thinking>`», «сначала распиши план рассуждений».
- «Волшебные слова» глубины (ultrathink и родня) — глубина задаётся параметром `effort`.
- Правила «не рассуждай / отвечай без размышлений» — при выключенном thinking они усиливают утечку служебных тегов.
- Капс, восклицательные знаки, «CRITICAL: YOU MUST» — дают overtriggering.
- Few-shot, который иллюстрирует очевидное. Оставляй примеры только там, где они задают формат или неочевидную границу.
- Разметку XML вокруг короткого и без того ясного промпта.

Правило остановки: если после удаления блока метрика не упала — блок был лишним.

## Шаг 2: что добавить (модель не угадывает это сама)

**Калибровка длины — три независимых канала.** Ни один не управляется параметром `effort`.

```
<tone_preference>
Держи ответы сфокусированными и короткими: оговорки сокращай, основную часть отдавай сути.
Ход работы комментируй экономно — одно предложение перед первым вызовом инструмента,
дальше обновления только при находке или смене направления; финал начинай с результата.
Длину файлов соотноси с задачей: раскрывай содержание, но не добивай объём
разделами-пустышками и повторными резюме.
</tone_preference>
```

В длинном системном промпте продублируй требование краткости коротким блоком ближе к концу — recency работает.

**Контракт задачи** — для узких правок, где модель склонна расширять границы:

```
<task_contract>
Цель: [что должно получиться].
В scope: [перечень].
Вне scope: [рефакторинг соседнего кода, новые файлы, переименования, тесты сверх запрошенных].
Критерий готовности: [проверяемое условие].
Если запрос выглядит ошибочным — скажи об этом одним предложением и делай как запрошено;
не подменяй задачу молча.
</task_contract>
```

Обратная сторона: для широкой задачи (крупная фича, новый модуль) тот же класс моделей работает лучше, когда получает **полную спецификацию заранее** и свободу исполнения, а не дробление на микрошаги. Различай режимы: узкая правка → жёсткий контракт; крупная фича → спецификация целиком.

**Лимит делегирования** — если у агента есть субагенты:

```
<subagents>
Делегируй только независимые ветки, которые реально идут параллельно, и не больше N за задачу.
Задачи с плотными зависимостями веди сам. Перед финальным ответом сверь утверждения
субагентов с их evidence — не пересказывай их отчёты как факт.
</subagents>
```

**Требование evidence вместо самоотчёта:**

```
<evidence>
Утверждение о выполненной работе подкрепляй проверяемым: пути созданных и изменённых файлов,
точный diff, команда и её фактический вывод. Не приводи вывод, которого не видел.
Отдельным списком — допущения, которые ты не проверял.
</evidence>
```

## Шаг 3: параметры, а не текст

- `effort`: low / medium / high (дефолт) / xhigh / max. Управляет объёмом размышления, **не** длиной видимого ответа. Для тяжёлого кодинга и длинных агентных прогонов стартуй с xhigh; `max` — только когда эвал показал запас качества выше xhigh. Выше не значит лучше: на повышенном effort фиксировались циклы самоперепроверки.
- **Не отключай thinking ради экономии — понижай effort.** Отключение доступно только при effort ≤ high (на xhigh и max запрос вернёт ошибку) и даёт два артефакта: вызов инструмента уходит в текст и не исполняется; внутренние теги протекают в ответ.
- При **выключенном** thinking модель чувствительна к слову «think» — пиши «consider», «evaluate», «reason through».
- `budget_tokens` не используй: параметр устарел, на новых моделях запрос отклоняется.
- Prefill последнего assistant-turn не поддерживается — формат задавай инструкцией или через tool use.
- Sampling-параметры (`temperature`, `top_p`, `top_k`) на новейших моделях не меняй.

Точные значения и коды ошибок сверяй по документации вендора — см. `sources.md`.

## Шаг 4: миграция уровней, а не перенос

Калибровка effort между поколениями не переносится. Стартуй с дефолтного высокого уровня и делай **effort sweep** на репрезентативных задачах: замерь качество и стоимость на соседних уровнях, зафиксируй самый дешёвый, который держит планку. Пошаговый протокол миграции целиком — `audit.md`, раздел «Миграция».

## Скелет промпта под Opus 5 (контракт)

Полный шаблон с плейсхолдерами — `template.md` §7. Порядок блоков: роль (одно предложение) → контракт задачи → калибровка длины → evidence → лимит субагентов → формат вывода → вход.

## Диагностика по жалобе

| Жалоба | Причина | Правка |
|---|---|---|
| Слишком многословно | Длина не задана ни по одному каналу | Блок `<tone_preference>`, три канала явно |
| Делает лишнее сверх задачи | Нет границ | `<task_contract>`: в scope / вне scope / критерий готовности |
| Жжёт токены на перепроверках | Осталась обвязка самопроверки | Удалить инструкции верификации; заменить критерием готовности |
| Плодит субагентов | Делегирование не ограничено | Блок `<subagents>` с числовым лимитом |
| Врёт про выполненные команды | Принимается самоотчёт | Блок `<evidence>`; лидер сверяет отчёты с артефактами |
| Стало хуже после смены модели | Промпт и параметры переехали одним куском | Протокол миграции по слоям (`audit.md`) |
| Ответы поверхностны на сложном | Слишком низкий effort | Поднимать effort, а не дописывать «думай глубже» |
