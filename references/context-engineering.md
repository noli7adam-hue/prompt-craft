# Context engineering: длинный контекст, кэш, агенты, экономия

Читай этот файл для: продакшн-промптов, агентов, работы с длинными документами, оптимизации стоимости/латентности. Prompt engineering — подмножество context engineering: управления ВСЕМ содержимым окна (системный промпт, инструменты, история, retrieved-документы, память).

## Три эмпирических факта, определяющих дизайн

1. **«Помещается в окно» ≠ «модель это использует».** Chroma «Context Rot» (18 фронтир-моделей): качество деградирует с ростом длины входа у ВСЕХ моделей, даже на простых задачах; это градиент, а не обрыв. NoLiMa (ICML 2025): на 32K токенах 10 из 12 моделей падают ниже 50% своего короткоконтекстного уровня. Сфокусированный промпт ~300 токенов стабильно бьёт полный ~113K на тех же задачах.
2. **U-образная кривая внимания («Lost in the Middle», Liu et al., TACL 2024).** Начало и конец контекста читаются хорошо, середина проваливается. Самое важное — к краям; gold-документ не закапывать в середину пачки.
3. **KV-cache — фактор дизайна, не только оптимизация.** Контексты с идентичными префиксами переиспользуют кэш: чтение кэша ≈ 10% базовой цены input у Anthropic/Gemini 2.5+ (у OpenAI 50%, автоматом). Manus называет hit-rate кэша важнейшей метрикой продакшн-агента.

## Раскладка окна для продакшн-промпта

```
[1] SYSTEM PROMPT (стабильно) — роль, правила, формат вывода
[2] TOOL DEFINITIONS (стабильно) — 3–5 ключевых инструментов
[3] MEMORY / RETRIEVED DOCS (полустабильно)
--- cache breakpoint здесь ---
[4] MESSAGE HISTORY (растёт)
[5] SCRATCHPAD / текущее состояние (волатильно)
[6] USER QUERY (волатильно)
```

Правила:
- **Стабильное — в начало, волатильное — в конец.** Даже однотокенное различие в префиксе (точный timestamp!) инвалидирует кэш. Дату, если нужна, помещай после breakpoint или огрубляй до дня.
- **Append-only + детерминированная сериализация** (порядок ключей JSON!) — иначе кэш ломается незаметно.
- **Не удаляй/добавляй инструменты динамически в середине сессии** — ломает кэш и путает модель ссылками на несуществующие тулзы.
- Anthropic: явные `cache_control` breakpoints (до 4), кэшируется префикс tools → system → messages; write +25%, read 10%. OpenAI: автоматически, ≥1024 токенов. Gemini: implicit по умолчанию + explicit.

## Системный промпт: «правильная высота»

Goldilocks zone: не хардкодить хрупкую if-else логику, но и не давать расплывчатых указаний. Структурировать секциями (XML или заголовки — одним форматом). Стремиться к минимальному набору информации, полностью описывающему поведение; ориентир — до ~2000 токенов для системной части. Каждая инструкция должна чинить измеренную ошибку — начинай с минимального промпта и добавляй блоки по результатам эвалов (принцип OpenAI и Anthropic).

## Инструменты агента

- Минимальный непересекающийся набор; «каждый инструмент оправдывает существование». Эвристика Anthropic: если инженер-человек не может однозначно сказать, какой инструмент использовать, — агент тем более не сможет.
- Порог: >10–15 инструментов → динамическая загрузка (Tool Search у Anthropic: −85% токенов на определениях).

## Длинные прогоны: compaction и внешняя память

- **Compaction** — суммирование истории при приближении к лимиту: сохранять архитектурные решения, нерешённые баги, детали реализации; выбрасывать избыточные tool-выводы. Риск: слишком агрессивное сжатие теряет тонкий критический контекст — сначала максимизируй recall резюме, потом повышай precision. У Anthropic есть server-side compaction и context editing (очистка старых tool-результатов — «самая безопасная форма compaction»).
- **Внешняя память / note-taking:** для задач длиннее одной сессии — файлы заметок (NOTES.md, todo, memory tool). Промотируй в память усвоенные решения, не сырые tool-выводы. В промпт агента: «Всегда просматривай директорию памяти перед началом работы».
- **Субагенты:** оправданы для breadth-first задач с независимыми параллельными ветками (research) — каждый работает в своём окне и возвращает сжатое резюме 1–2K токенов; цена ~15× токенов. Для задач с плотными зависимостями (большинство кодинга) надёжнее один агент с компакцией.

## Экономия токенов — приёмы с лучшим соотношением эффект/усилие

1. Prompt caching (структура выше) — до 90% на input.
2. Batch API — −50% на несрочных задачах (OpenAI, Anthropic).
3. Роутинг моделей: дешёвые (Haiku/Flash/mini) на простые задачи.
4. Контроль reasoning effort: у GPT-5 «minimal» против «high» — разница в десятки раз по токенам.
5. Снижение output: просить краткость, `max_tokens`, structured output, diff вместо целого файла.
6. RAG вместо свалки в длинное окно.
7. Дешёвые форматы данных (YAML/CSV вместо JSON) — ~28–33% на однородных табличных данных.
8. Английский язык промпта — на 20–40% меньше токенов для нелатинских языков.

## RAG-специфика для промптера

Галлюцинации в RAG — чаще всего провал retrieval, а не промпта (до 67% галлюцинаций в conversational RAG — «extractive»: модель верно воспроизводит неверный извлечённый контент). Прежде чем «чинить промпт», продиагностируй:

- Низкий context recall → чини retrieval (эмбеддинги/чанкинг/поиск), промпт не поможет.
- Retrieval хороший, но низкий faithfulness → вот теперь проблема промпта/модели: усиливай grounding («сначала процитируй в `<quotes>`, потом отвечай в `<answer>`»; «если ответа нет в документах — скажи явно»).
- Если база <200K токенов (~500 страниц) — RAG может быть не нужен: помести всё в кэшируемый промпт.
