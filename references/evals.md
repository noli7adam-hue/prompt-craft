# Оценка промптов: эвалы, итерация, регрессии

Читай этот файл, когда: промпт идёт в продакшн; пользователь жалуется «работает нестабильно»; нужно сравнить варианты промпта; нужно пережить смену версии модели.

## Базовый цикл (Anthropic)

Определить критерии успеха → построить эвалы → написать промпт → добавить контекст → итерировать. Пропуск эвалов — главная причина «вчера работало» и несогласованности внутри команды. Промпт без способа проверки — не готов.

## Минимум для любого промпта (даже разового)

Прогон на 3–5 реальных входах, обязательно включая:
- типичный «счастливый путь»;
- краевой случай (пустой/некорректный/неоднозначный ввод);
- пограничный случай между категориями/режимами;
- для промптов на недоверенном контенте — вход с встроенной «командой» (проверка инъекционной гигиены).

Если хоть один вход валит промпт — чини до выдачи пользователю.

## Правила итерации

- **Одно изменение за раз** (правило OpenAI): сначала модель, потом параметры (effort/thinking), потом текст промпта; замер после каждого шага. Иначе не поймёшь, что сработало.
- **Добавляй блок в промпт только когда он чинит измеренную ошибку.** Начинай с минимального промпта; каждая строка должна оправдывать существование.
- **Позитивные И негативные примеры** в эвал-наборе: негативные определяют границы и предотвращают overtriggering.
- **Закрепляй снапшот модели** в проде. Поведение дрейфует между версиями; при апгрейде — обязательный регрессионный прогон полного набора до выкатки. Кэш между моделями не переносится.
- **Каждый продакшн-сбой → новый регрессионный тест.**

## Метрики

Уходи от «вайбов» к измерению:
- **Детерминированные проверки** — для точного: exact-match, валидность JSON по схеме, наличие обязательных полей, имена инструментов. Дёшево, гоняй на 100% случаев.
- **LLM-as-judge** — для субъективного: релевантность, faithfulness/groundedness, полнота, ясность. Обязательно валидируй судью против человеческой разметки (расхождение → чини промпт судьи); в промпт судьи включай рассуждение перед оценкой (шаблон judge — в `patterns.md`). Судья оценивает результат, а не «правильный путь» (агентные прогоны недетерминированы).
- **Человеческая разметка** — 2–5% для калибровки и краевых случаев.

Каскад: детерминированное на всём → LLM-судья на выборке и на 100% CI-регрессий → человек на калибровке.

## Диагностика по симптомам

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| Формат вывода плавает | Схема только в прозе | Structured Outputs / tool use; один пример формата; валидация + ретрай |
| Модель отвечает не по документам (RAG) | Сначала проверь retrieval | Низкий recall → чини retrieval; recall высокий → усиливай grounding в промпте |
| Ответы нестабильны от прогона к прогону | Неоднозначные правила, нет тай-брейкеров | Явные правила разрешения конфликтов; для критичного — self-consistency (несколько прогонов + большинство) |
| Модель «перестарается» / паникует | Капс, угрозы, «CRITICAL» | Смягчить до ровного тона |
| Модель недодаёт | Расчёт на домысливание | Запрашивать полноту явно (буквальность 4.x/5.x) |
| Reasoning-модель стала хуже после «улучшений» | Добавили CoT/примеры | Убрать; вернуться к outcome-first |
| Стало дорого/медленно без роста качества | Лишний thinking | Снизить effort/thinking_level; если wrong-answer rate не отличается — отключить |

## Построение golden dataset

- Создавай рано, под конкретный use case. Каждый пример: вход → ожидаемый выход (или критерии приемлемости) → пометка «позитивный/негативный/краевой».
- Можно генерировать кандидатов LLM-ом, но с обязательной ручной верификацией.
- 10–20 примеров достаточно для старта; расширяй по мере обнаружения провалов.

## Формулировка assert'ов для промпта

Хороший критерий проверяем бинарно: «ответ содержит ровно одно слово из списка категорий», «JSON валиден по схеме и все даты в ISO 8601», «в ответе нет URL», «при пустом вводе возвращается other». Плохой: «ответ качественный».
